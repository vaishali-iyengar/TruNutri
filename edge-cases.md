# Edge Cases

Corner scenarios to check off against [implementation-plan.md](implementation-plan.md). Organized by the phase that owns the fix. Use this as a test checklist during each phase's manual testing, not just the happy path in the plan.

Status markers: `[x]` verified handled, `[ ]` not yet verified.

## Data Layer (Phase 1)

- [ ] `DATABASE_URL` unreachable at startup — backend should fail loudly on first query, not hang or silently retry forever.
- [ ] Migration run twice against the same database — `drizzle-kit migrate` should no-op, not error or duplicate tables.
- [ ] Postgres connection pool exhaustion under concurrent requests — confirm `pg.Pool` default size is sane for expected concurrent chat users; no unbounded connection growth.
- [ ] Inserting a `messages` row with a `conversation_id` that doesn't exist — FK constraint should reject it, not insert an orphan.

## Model Call (Phase 2)

- [ ] Model returns no `tool_use` block at all (e.g. it responds with plain text despite `tool_choice`) — `callModel()` must return `{ parsed: null, error: "no_tool_use_block" }`, not throw.
- [ ] Model returns a `tool_use` block whose `input` is valid JSON but missing a required field (e.g. no `claims` key) — Zod `safeParse` fails cleanly, `error` is populated.
- [ ] Model returns a `claims[].source` that is a string instead of `null` (model ignores the schema) — must fail Zod validation (`z.null()` rejects it) rather than being silently coerced.
- [x] Groq API call itself throws (network error, 429 rate limit, 500, invalid API key) — fixed in Phase 5: `chatRouter` catches this and logs a `model_error` failure row rather than crashing the request.
- [ ] Groq API call times out — decide and enforce a timeout (SDK default or explicit `timeout` option) so a hung request doesn't hold the HTTP connection open indefinitely.
- [x] **New, found during Phase 7 deployment:** Groq removed `llama-3.3-70b-versatile` from their model catalog entirely (a live smoke-test request returned 404 `model_not_found`, confirmed independently via `GET /v1/models`) — this broke local dev too, not just the deployment, since it's a provider-side change, not an environment difference. There's no code-level guard against a configured model silently disappearing; the failure surfaces correctly as a `model_error` (502, logged) rather than crashing, but nothing proactively warns before that point. Fixed by switching the default to `openai/gpt-oss-120b` and re-verifying the full eval suite plus multi-turn conversations. Worth periodically checking `GET /v1/models` against `GROQ_MODEL` if this recurs.
- [ ] Empty user message reaches `callModel()` (should be caught earlier by the `!message` check in the route, but confirm) — verify the 400 response actually fires before any model call.
- [ ] Very long user message (multi-paragraph paste) — confirm it doesn't blow past `max_tokens` context in a way that silently truncates history; decide whether to cap input length.
- [ ] Non-English or gibberish input — confirm the model doesn't produce an `answer` that itself trips the scope guard in an unexpected language (regexes are English-only, so non-English scope violations won't be caught — worth noting as a known gap).

## System Prompt & Evals (Phase 3)

- [ ] A prompt edit fixes one eval question but flips another from pass to fail — the diff output in `run.ts` must surface this (this is the whole point of the eval; verify it actually catches a deliberately-introduced regression once).
- [ ] Eval run crashes partway through (e.g. one question causes an uncaught exception) — confirm it doesn't silently produce a partial/misleading snapshot; decide whether one failed question should abort the whole run or just be recorded as a failure.
- [ ] Running `npm run eval` with no `results/` snapshots yet — first run should still succeed and just skip the diff section (verify `priorFile` being `undefined` doesn't crash the script).
- [ ] Two eval runs in the same second — timestamp-based filenames use ISO strings with `:`/`.` replaced, but confirm no filename collision under fast repeated runs.
- [x] **(problem-statement.txt update, implemented; cap later raised 300 → 1000):** the system prompt requires answers under a character cap (originally 300, raised to 1000 in a later problem-statement.txt update — `MAX_ANSWER_LENGTH` in `run.ts` and the prompt text both updated to match). `run.ts` flags (`overLength: true`, printed `⚠`) any answer over the cap as a visible warning, but this is deliberately not a pass/fail and nothing in `chatRouter`/the schema rejects or truncates an over-length answer in production — the problem statement only calls out *scope limits* as needing code enforcement, not length. Verified live at both cap values: 15/15, no flips, zero length warnings.
- [x] **(problem-statement.txt update, implemented):** the system prompt now asks the model to cite a source briefly inline within `answer`/`claims[].text` (e.g. "…per USDA guidance"), while `claims[].source` still stays `null`. Spot-checked the new eval snapshot: all 8 in-scope answers included a general, plausible-sounding attribution ("per USDA guidance," "CDC guidance," "FDA nutrition guidance") rather than a fabricated specific study or statistic — but this was only checked by eye across one run, not asserted in code, so a future run producing a suspiciously specific fake citation wouldn't be caught automatically.
- [ ] The system prompt now allows bullet-formatted answers. `run.ts`'s diff is only on `matchesExpectation` (the scope-category outcome), not on `answer` text equality, so formatting-only changes between runs do **not** cause false "flips" — confirmed by inspection of the diff logic, not by deliberately forcing a bullet/prose alternation on the same question. Still open as a live test.
- [x] **Real regression, caught and fixed by the eval suite:** a prompt change asking the model to "fold in" the source as a natural conversational aside (rather than a formal trailing citation clause) caused the model to also start populating the structured `claims[].source` field with the org name (e.g. `"USDA"`) instead of `null`, on 3 of 15 questions. Groq's own tool-call schema validation rejected these responses outright (400 `tool_use_failed`), surfacing as `[ERR]` in the eval output — this is exactly the "fixed one thing, broke another" scenario the eval suite exists to catch, and it worked as designed. Fixed with an explicit, unambiguous rule stated separately from the tone/style guidance: `source` is always the literal `null`; mentioning a source in the writing and filling the structured field are different things. Re-verified twice after the fix: 15/15, no flips.

## Scope Enforcement (Phase 4)

- [x] Borderline phrasing that *sounds* medical but isn't — e.g. "is honey safe for babies" (food-safety question, not medical advice) — must **not** be declined; verify the regex categories don't over-match on words like "safe." Confirmed via eval question "Is honey safe to give to a one-year-old?" — passes as in-scope.
- [x] Scope-relevant question phrased indirectly — e.g. "my doctor said I should lose 10 pounds, how do I do it" — pre-model regex may miss this (no direct trigger phrase). Confirmed missed initially; fixed in Phase 4 by adding a specific-weight-change-amount pattern (`(lose|gain) \d+ (pounds|lbs|kg...)`), now caught pre-model.
- [x] Mixed-intent message — one in-scope question and one out-of-scope question in the same input (e.g. "how do I store fish, and how many calories should I eat?") — current guard flags the whole message if *any* pattern matches, meaning the in-scope half also gets declined. Confirmed this is the intended behavior (fail closed): `checkScope("How do I store fish, and how many calories should I eat?")` returns `calorie_or_weight_target`, while the in-scope half alone returns `null`.
- [x] Case sensitivity / punctuation variants — "HOW MANY CALORIES SHOULD I EAT???" — regexes use the `i` flag, so casing is covered; confirmed punctuation doesn't break the match.
- [ ] Scope guard false-negative that reaches the model, and the model itself declines appropriately in prose — confirm this still gets logged as a `scope_violation` if the post-model check's regex also matches the model's own refusal wording (e.g. model's answer might contain "I can't help with that" plus a restated calorie phrase — verify no double-decline weirdness).
- [ ] A follow-up message that's in-scope on its own but references an earlier declined message (e.g. user says "ignore that, tell me about fiber instead") — confirm the current message still gets checked independently; conversation history shouldn't cause a false decline.

## Chat Endpoint (Phase 5)

- [x] Missing `conversationId` on first message (`null`) vs. an invalid/garbage `conversationId` (not a valid UUID, or a UUID that doesn't exist in the DB) — **found to actually crash the entire Node process**, not just return a 500 (Express 4 doesn't auto-catch async route errors, so the unhandled FK-violation exception took the whole server down). Fixed: `conversationId` is validated as a well-formed UUID (400 if not) and checked for existence (404 if not found) before any insert is attempted; the whole handler is also now wrapped so nothing in it can crash the process again.
- [x] Request body missing entirely or malformed JSON — added JSON-parse-error middleware in `index.ts`; confirmed a malformed body now returns a clean 400 JSON error instead of Express's default HTML error page.
- [ ] Concurrent messages sent for the same `conversationId` (double-click send, or two browser tabs) — no locking around history read + insert; two requests could read the same prior history and both append, producing an odd but not corrupt ordering. Not yet tested live; worth a note even if not fixed for the prototype.
- [x] Schema validation failure (Phase 2 case) reaching the route — 502 response path confirmed live (see Phase 3/5 testing); a `model_error` variant (Groq API itself rejecting the call, e.g. `output_parse_failed` or `tool_use_failed`) was also found and is now handled the same way (502 + `failures` row).
- [ ] DB insert fails after a successful model call (e.g. connection drop mid-request) — still unhandled as a *specific* case, but the whole-handler try/catch added in Phase 5 means it will at least surface as a clean 500 via the catch-all error middleware rather than crashing the process; no failure row is recorded for this specific scenario yet.
- [ ] `/health` endpoint hit while DB is down — currently always returns `{ ok: true }` regardless of DB state; decide if that's acceptable for a "health" check or if it's misleading for Railway's health checks.
- [x] **Fixed — root cause found (was: found during Phase 5 testing, hit again in real use on a plain content follow-up, not just meta-questions):** any follow-up turn (not just self-referential meta-questions — e.g. "How about buffalo milk?" after "How much protein does milk have?") could make the model skip the forced tool call and return nothing, which Groq rejects with a 400 `tool_use_failed`. The earlier "fix" (stronger prompt wording + a one-shot retry nudge) reduced but did not eliminate this — it failed twice in a row on a real multi-turn conversation. Root cause: prior assistant turns were replayed to the model as plain `{role: "assistant", content: "..."}` text, while `tool_choice` was only forced on the *current* turn — an inconsistent conversation shape that made the model treat later turns as ordinary chat. Fixed structurally in `backend/src/model/client.ts`: each prior assistant turn is now reconstructed as the actual `tool_calls` + `tool` result pair the model would have produced (using the `claims` already stored per message in Postgres), so the whole conversation looks consistently tool-using, not just the newest message. The nudge-retry stays as a secondary safety net. Verified: 5 different multi-turn conversations (mix of content follow-ups and meta-questions) all succeeded with zero failures logged, and the full eval suite still passes 15/15 with no flips.
- [x] **New, found during Phase 5 testing:** `zodToJsonSchema()`'s output includes a top-level `$schema` meta key. Leaving it in the function-calling `parameters` object made tool-calling unreliable on multi-turn conversations (the fix for the meta-question case above did *not* fix this one — they're separate issues). Fixed by stripping `$schema` before sending to Groq.

## Frontend (Phase 6)

- [x] Backend unreachable (wrong `NEXT_PUBLIC_BACKEND_URL`, backend down, CORS misconfigured) — confirmed live with Playwright (backend killed mid-session): "Couldn't reach the server. Try again." renders, and `pending` correctly resets (input re-enabled, not stuck).
- [ ] Backend returns non-JSON (e.g. a proxy/CDN error page) — `res.json()` will throw; confirm this is caught by the existing `try/catch` and doesn't crash the page.
- [ ] Backend returns a 502 (schema validation failure) — confirm the frontend's `!res.ok` branch renders `data.error` correctly rather than assuming every non-declined response has an `answer` field.
- [ ] `localStorage` unavailable (private browsing mode blocking storage, or SSR execution) — the `useEffect` reads happen client-side only, which is correct for Next.js, but confirm no `localStorage` access happens during server render.
- [ ] User sends a message, then immediately clicks "New conversation" before the response arrives — the in-flight request will still resolve and call `setMessages`/`setConversationId` against the now-cleared conversation. Decide whether to ignore stale responses (e.g. via a request id/abort controller).
- [ ] Rapid double-submit (pressing Enter twice fast, or clicking Send while `pending` is momentarily stale) — `sendMessage` checks `pending` at call time; confirm React state batching doesn't allow a race where two requests fire.
- [ ] Empty or whitespace-only input — `text.trim()` guard should block this; confirm the Send button's `disabled={!input.trim()}` matches.
- [ ] Very long conversation (50+ turns) — message list has no virtualization; confirm scroll performance is acceptable for a prototype, or explicitly accept the limitation.
- [x] **Superseded:** claims are no longer aggregated into the sidebar (an earlier design pass moved them to inline per-message rendering, with the sidebar now a static "Sources coming soon" placeholder per problem-statement.md's Milestone-2 note) — so the original concern here (duplicate claims piling up in one aggregated list) no longer applies. Each message renders only its own claims.
- [x] **(problem-statement.txt update, implemented):** the system prompt now allows bullet-formatted answers (e.g. `- item` lines). Added a lightweight `AnswerText` component in `page.tsx` that splits on newlines and renders consecutive `- `/`• `/`* ` lines as a real `<ul>`, falling back to a plain paragraph for prose. Verified with a real bullet answer from the eval baseline (the vitamin-C question) via a mocked API response in Playwright — renders as an actual bulleted list, with the trailing citation line as a separate paragraph below it. Not tested: nested bullets, numbered lists, or bold/italic markdown syntax (none of which the system prompt currently asks for).
- [x] **New, found during Phase 6 testing:** reloading the page keeps `conversationId` in `localStorage` (confirmed identical before/after reload) and the backend genuinely still has the full message history for it (confirmed in Phase 5) — but the frontend has no code path that fetches and redisplays that history, so the visible chat resets to empty on reload even though the underlying conversation is intact. A user reloading mid-conversation would reasonably read this as "my history is gone," even though a new message would still get a contextually correct answer from the backend. Not fixed — needs a new `GET /api/conversations/:id/messages`-style endpoint, which isn't part of the current architecture.

## Deployment (Phase 7)

- [x] `FRONTEND_ORIGIN` set before the real Vercel URL exists — CORS will reject the deployed frontend's requests until this is updated; this is explicitly called out as a two-step process in the plan. **Real incident, twice:** first, a trailing slash on the env var caused the exact mismatch this item warns about, live in production (real user report: "connection error" when asking a question). Root cause: `cors()` just echoes `FRONTEND_ORIGIN` verbatim — there's no Railway-side header rewriting, contrary to an earlier note here that claimed there was. That earlier conclusion came from testing the header immediately after an env var change, while the *previous* deployment (still holding the old value) was still live — a race with the redeploy, not a platform quirk. Fixed by setting the var to the exact origin with no trailing slash, and — critically — confirming the redeploy had actually finished before re-testing, instead of a fixed `sleep`. **Lesson:** always verify deployment status directly (e.g. `railway deployment list`) rather than assuming a short sleep is long enough, especially when re-testing something that just changed.
- [x] **New, found during Phase 7:** Vercel project had `rootDirectory`/`framework` both `null` (same failure class as the Railway orphaned-service issue) — the "Ready" deployment's build log showed zero install/build steps and "no files were prepared," so every route 404'd despite a green deployment status. Fixed via the Vercel API (`PATCH /v9/projects/:id` with `rootDirectory: "frontend"`, `framework: "nextjs"`), then a fresh deployment. Dashboard-only inspection didn't surface this clearly (the project's Settings → General didn't even show a Root Directory field for this user) — found conclusively by querying the API directly and reading the actual build event log.
- [ ] Railway backend restarts (deploy, crash, scale event) — in-memory state is none (good, everything's in Postgres), but confirm `DATABASE_URL` env var persists correctly across restarts via the Railway Postgres add-on binding.
- [ ] Vercel preview deployments (PR branches) — these will get a different URL than production and won't match `FRONTEND_ORIGIN`; decide whether CORS needs to allow a wildcard/pattern for preview URLs or whether that's out of scope for the prototype.
- [ ] Cold start latency on Railway after idle — first request post-idle may be slow; confirm this doesn't trip a frontend timeout or read as a network error.
- [ ] HTTPS mixed-content — confirm `NEXT_PUBLIC_BACKEND_URL` is `https://` in production; an `http://` backend URL from a `https://` Vercel frontend will be blocked by the browser.

## Rules Compliance (Phase 8, cross-cutting)

- [ ] A response that partially matches the schema but has extra unexpected fields — confirm Zod's default (strip unknown keys) doesn't mask a case where the model is returning something structurally wrong in a way that should count as a failure.
- [ ] Confirm there is no code path — including error paths — where `source` could be anything other than `null` (e.g. an error-handling shortcut that echoes back user-provided data into a claim).
- [x] **(problem-statement.txt update, verified for current state):** now that the system prompt asks for a short inline citation *inside* `answer`/`claims[].text`, confirmed this hasn't become a backdoor around "source fields must stay null" — `ClaimSchema.source` is still hardcoded `z.null()` in `backend/src/schema/response.ts` (untouched by this change), and nothing in `callModel()` or `chatRouter` reads the inline text back out into the `source` field. This is a standing invariant, not a one-time fix — re-check it if `source` handling is ever touched again (e.g. when Milestone 2 wires up real sources).
- [ ] Confirm a failure event is never "handled" by silently retrying the model call and discarding the first failure — re-check `chatRouter` and `callModel` for any retry logic that might get added later without a matching `failures` insert.
